## 零、AI 使用原则与工具说明

**使用的工具**：DeepSeek 对话式编程助手（网页端与 IDE 插件），主要用于方案对比、代码片段生成、报错定位与文档润色；数据库设计、关键业务逻辑、最终集成与验收由我本人完成并逐行核对。

**我的六条原则**：

1. **先想清楚再提问**：提问前先自己把问题拆成"背景 / 现状 / 我期望的结果 / 已尝试的做法"，避免一句话让 AI 替我决策。
2. **AI 出方案，我做取舍**：AI 给的是候选项，不是结论。技术选型必须结合课程要求（题目三、技术栈限定、一人独立完成）自己拍板。
3. **代码必须跑通才算数**：AI 给的代码一律在本地跑，报错就贴报错继续问，绝不直接粘贴进项目。
4. **关键逻辑自己写一遍**：金额校验、数据隔离（`user_id` 过滤）、统计聚合这些直接影响正确性与安全性，必须自己能讲清每一行。
5. **不让 AI 编事实**：文档里的表结构、接口、命令，最后都以实际代码和实际运行结果为准逐条核对。
6. **记录迭代过程**：把多轮提示词和"AI 错在哪、我改了什么"记下来，比只留一份最终代码更有复盘价值。

**说明**：以下"提示词"为真实提问的整理版（保留当时的上下文与迭代轮次），AI 回复摘要为要点归纳，最后一节"我的修改与采纳"才是这份记录的核心——它体现的是我在哪些地方**没有**直接采纳 AI 的建议。

## 一、选题与技术方案对比

**意图**：从题库题目三出发，确定技术栈与整体形态（服务端渲染还是前后端分离），并评估"一人独立完成 + 6 周"的可行性。

**提示词**（多轮）：

> 第 1 轮：我是计算机相关专业大三学生，课程是《Python Web企业级项目开发》，课程设计要求从题库选题，一人独立完成，周期大约 6 周。我选了"题目三：个人记账本（收支管理 + 图表统计）"。课程指定 MySQL 8.0 和 Flask 体系，但我还没决定是做成 Flask + Jinja2 服务端渲染，还是 Flask 只做 API、前端用 Vue。请分别分析两种路线对这个题目的工作量、技术风险和我能写进答辩的技术点，不要直接推荐，先列对比维度。
>
> 第 2 轮：按你列的维度，我倾向于服务端渲染，因为一个人做前后端分离会额外花时间在 JWT、路由守卫、跨域和构建工具上。但统计页要求"筛选联动刷新"，纯服务端渲染是不是必须整页刷新？有没有轻量方案？
>
> 第 3 轮：如果统计页用 3 个 fetch 并行拉 JSON 接口，我在答辩时怎么说明这不是"前后端分离"？另外 ECharts 用 CDN 会违反课程"资源本地化"的要求吗？

**AI 回复摘要**：对比表指出前端分离路线的额外成本主要在鉴权与工程化脚手架，对本题业务量而言收益低；服务端渲染 + Ajax 局部刷新是"混合模式"，统计页用 `fetch` 拉 JSON 只刷新图表容器，页面主体仍是 Jinja2；ECharts 建议下载 `echarts.min.js` 放 `static/vendor/`，与 Bootstrap 一起本地化，理由是可离线演示、不受校园网限制。

**我的修改与采纳**：
- 采纳服务端渲染主线，但**没有采纳 AI 建议的"每个图表一个独立 HTML 片段接口"**——那会让模板碎片化，最终改为全部返回统一 JSON `{code:0,data:...}`，前端一个渲染函数处理，接口文档也更好写。
- AI 第 3 轮回答里说"CDN 不影响课程评分"，这一点我**没有采纳**：课程明确要求前端依赖本地化，答辩时断网演示是硬需求。我把 vendor 目录写进了目录结构和 README。
- AI 给的 6 周排期是按"每周 15 小时"估算的，我按自己实际每周 10 小时左右重新排了里程碑（见 `DEVELOPMENT_LOG.md`），把测试与文档压缩到最后一周。

## 二、数据库表设计评审

**意图**：在动手写代码前，用 AI 充当评审，检查五张表（user/account/category/record/budget）的字段、类型、索引与删除策略是否有明显问题。

**提示词**（多轮）：

> 第 1 轮：我设计的记账本有五张表：user、account（资金账户）、category（收支分类）、record（记账条目）、budget（月度预算）。record 的金额字段我打算用 DECIMAL(10,2)，type 用 varchar 存 expense/income，category_id 和 account_id 允许为空。请评审：哪些字段类型有隐患？索引应该怎么建？我先说我的查询模式：流水列表总是"当前用户 + 年月 + 可选类型/分类/关键词"，统计总是"当前用户 + 日期区间"。
>
> 第 2 轮：你说 category_id 外键用 SET NULL 是对的。但我担心用户删了分类以后，历史记录的金额还在但分类没了，饼图会少算。这个怎么处理？
>
> 第 3 轮：你建议给 record 建 (user_id, record_date, type) 三列索引，我只有 (user_id, record_date) 和 (user_id, category_id)。三列会不会更好？请从"范围查询后一列失效"的角度分析。

**AI 回复摘要**：第 1 轮指出金额必须 DECIMAL、分类的 `name+type` 要建唯一约束、账户名要按用户唯一；第 2 轮建议统计 SQL 用 `LEFT JOIN category` 并把 NULL 归类为"未分类"，用 `COALESCE` 或 Python 侧兜底；第 3 轮承认 `type` 放在 `record_date` 之后意义有限，因为第二个条件已经是范围列，第三列用不上索引，建议保持 `(user_id, record_date)` 即可。

**我的修改与采纳**：
- **否决了 AI 最初建议的"在 record 上冗余存 category_name 快照"**：这会让改名分类出现历史与当前不一致，且额外维护成本高。最终用 `LEFT JOIN` + "未分类"兜底，逻辑更干净。
- AI 第 1 轮还建议"给 `note` 加 FULLTEXT 索引做关键词搜索"，我**没有采纳**：MySQL 中文全文检索默认分词器对中文支持差（需要 ngram parser 且调整 `innodb_ft_min_token_size`），课程项目里 `LIKE '%关键词%'` 配合分页完全够用，而且数据量在千级。这个取舍我写进了设计文档 6 节。
- 采纳了 `(user_id, record_date)` + `(user_id, category_id)` 两个复合索引，并额外补了 `category` 表的 `(user_id, type)`，因为分类下拉框是按类型加载的。
- AI 说"金额上限随便设 99999999.99 就行"过于随意，我按课程要求的 8 位整数 + 2 位小数反推出 `DECIMAL(10,2)`，并在校验层同步了上限常量，保证数据库与校验规则一致。

## 三、Flask 应用工厂与蓝图拆分

**意图**：设计 `create_app()` 工厂、扩展单例模块和三个业务蓝图（auth / ledger / stats），避免循环导入。

**提示词**（多轮）：

> 第 1 轮：我的项目要用应用工厂模式 + 蓝图，目录是 app/{__init__.py, extensions.py, models.py, utils.py, auth/, ledger/, stats/}。请给我一个 create_app 的骨架，要求：支持通过参数传入配置类名或字典、注册蓝图、注册 404/500 错误处理、注册 Jinja 自定义过滤器。注意 models.py 里会用 db，不要产生循环导入。
>
> 第 2 轮：我按你的结构写完，运行 `flask --app run.py init-db` 报 `RuntimeError: The current Flask app is not registered with this 'SQLAlchemy' instance`。另外登录时 `login_manager.user_loader` 好像没生效，一直提示未登录。帮我定位。
>
> 第 3 轮：我打算把"注册时初始化默认分类和账户"放在 auth 蓝图里，但默认分类列表定义在 models.py。这样 auth 依赖 models 是否合理？还是应该放到 models 的方法里？

**AI 回复摘要**：第 1 轮给出工厂骨架，强调扩展在 `extensions.py` 中创建、在工厂内 `init_app`；第 2 轮指出 `user_loader` 必须在 `login_manager.init_app(app)` 之后、且要在应用上下文已建立时注册，另外 CLI 命令报错是因为命令写在 `__init__.py` 但在 `app.app_context()` 之外执行 `db.create_all()`；第 3 轮建议把默认分类常量留在 `models.py`，由 `User` 的一个类方法或注册服务函数统一处理，避免蓝图之间互相依赖。

**我的修改与采纳**：
- 采纳了"扩展单例 + 工厂内 init_app"的结构，`db / login_manager / csrf` 三个对象严格放在 `extensions.py`，这是避免循环导入的关键。
- **AI 第 2 轮的定位有一半是错的**：它说 `user_loader` 要"在 init_app 之后注册"，实际我核对文档后发现 `user_loader` 是装饰器，注册顺序不影响，真正原因是我的 `create_app` 里提前 `return app` 导致 init_app 那段没执行（缩进错误）。我自己打断点定位后修正，没有照搬它的解释——这提醒我不能把 AI 的"根因"当圣旨。
- 我把默认分类/账户的初始化**没有**放在 auth 蓝图的注册视图里散着写，而是抽成 `models.py` 的 `DEFAULT_CATEGORIES` / `DEFAULT_ACCOUNTS` 常量和初始化函数，由注册流程调用。这样 seed 脚本也能复用同一份数据，避免两处维护。
- AI 建议把 CLI 命令放在 `app/cli.py`，我采纳并简化：`init-db` 与 `seed-demo` 两个命令，前者建表、后者灌演示数据，README 的快速开始就是按这两个命令写的。

## 四、金额精度（float → Decimal）与 SQL 聚合写法

**意图**：解决"页面合计与 CSV 合计差 1 分钱"和"统计接口慢、`EXPLAIN` 显示全表扫描"两个问题。

**提示词**（多轮）：

> 第 1 轮：我的记账应用金额字段数据库是 DECIMAL(10,2)，但 Python 里校验完 `round(float(text), 2)` 再赋给模型。现在发现连续记 3 笔 0.1、0.2、0.3 的账，页面显示的月度合计和手算差 0.0000000001 那种数。另外 `jsonify(汇总结果)` 报 `TypeError: Object of type Decimal is not JSON serializable`。这两件事是不是同一个原因？请给最小改动的方案。
>
> 第 2 轮：统计接口我原来是把当月记录 `all()` 出来在 Python 里循环累加，现在改成 SQL 聚合，写法是 `db.session.query(func.sum(Record.amount)).filter(Record.user_id==uid, ...)`。但趋势图要按年月分组，我写成 `func.year(Record.record_date), func.month(...)`，`EXPLAIN` 显示 type=ALL。课程要求写清楚为什么不能用 YEAR() 函数，帮我组织这部分论证，不要只给结论。
>
> 第 3 轮：跨 6 个月的查询，是循环 6 次查一次月，还是一次查 6 个月再在 Python 里按年月拆？两种在 MySQL 上的执行计划和可读性差别大吗？

**AI 回复摘要**：第 1 轮明确两件事同源——float 参与累加导致误差、Decimal 不能直接 JSON 序列化；建议"入口处 float 解析一次 → 立即 `Decimal(str(x)).quantize(Decimal('0.01'))` → 入库"、"序列化层统一转 float 或格式化字符串"，并给了 `func.coalesce(func.sum(...), 0)` 的兜底写法。第 2 轮解释了 `WHERE YEAR(col)=?` 会使索引失效的机制，建议改成 `record_date >= start AND record_date <= end`，并给出 `DATE_FORMAT(record_date,'%Y-%m') AS ym` 做 SELECT/GROUP BY 的写法。第 3 轮建议一次查 6 个月再在 Python 里按年月拆分，理由是减少往返、且月份补齐逻辑本来就在 Python 侧。

**我的修改与采纳**：
- 采纳 Decimal 方案，但**没有照 AI 的"整个应用全程用 Decimal"**：那样前端展示和 JS 计算也要处理字符串，改动面太大。最终定的是"计算层 Decimal、展示层 float/千分位字符串"的边界，并用 `fmt_money` 过滤器统一格式化。这个边界写进了设计文档 5.8 和 6.1。
- AI 给的"循环 6 次查月"在可读性上更好，但它自己也承认"6 次往返在千级数据下没有性能问题"。我最终**采纳了逐月聚合**，但没有采纳它配套的 `DATE_FORMAT` 分组方案——因为测试库是内存 SQLite，没有 `DATE_FORMAT`，两套方言会让测试和生产逻辑分叉。最终保留"6 次窄区间聚合 + Python 拼标签"，并在设计文档 5.2 写清了"为什么宁可多 5 次往返"的可移植性理由。
- 采纳了 `coalesce(sum(...), 0)` 兜底，但发现**更大的坑是分组结果为空时 Python 侧 `sum([])` 返回 int 而不是 Decimal**，导致类型不一致。我在聚合结果统一 `float()` 转换处加了 `or 0` 兜底。
- 关于"为什么用日期区间不用 YEAR()"，AI 只给了"索引失效"一句结论。我按它给的机制自己补了 `EXPLAIN` 对比截图与执行计划说明，把论证扩写成"索引失效 + 边界统一由工具函数生成 + 可验证"三点，见设计文档 5.7。

## 五、ECharts 联动与空数据兜底

**意图**：统计页三张图 + 热力图 + TOP5 需要随筛选联动刷新，并处理无数据、部分接口失败、切主题时图表配色不变等问题。

**提示词**（多轮）：

> 第 1 轮：统计页有 5 个图表 + 4 张指标卡，全部由同一个"年月"筛选控制。现在是点一次筛选发 6 个请求（概览 + 5 个图表），我想用 `Promise.all` 等全部返回再统一渲染，但怕某个接口挂掉整页白屏。有没有更稳的做法？另外无数据月份 ECharts 会不会出现 NaN？
>
> 第 2 轮：我按你说的用 `Promise.all` 包了一层，但觉得 `allSettled` 的 `fulfilled/rejected` 状态判断太啰嗦。如果我在每个请求外先 `.catch(() => null)`，再统一 `Promise.all`，是不是能同时做到"局部失败不影响整体"又少写分支？另外未登录时点击筛选，控制台报 `Unexpected token '<'`，因为后端 302 到登录页返回了 HTML；切到深色主题后图表还是白底黑字，很突兀。分别怎么处理？
>
> 第 3 轮：折线图我按月分组只有 4 天有数据，结果折线直接把 4 个点连起来，X 轴也只显示这 4 天。我期望显示当月 1~31 号完整刻度，没有数据的日期为 0。这个补齐应该在后端做还是前端做？

**AI 回复摘要**：第 1 轮建议 `Promise.allSettled` + 每个图表独立空状态；空数组会触发 ECharts 的坐标轴自动计算异常，建议空数据时不调 `setOption` 而显示占位。第 2 轮：`fetch` 默认 `redirect: 'follow'`，应封装统一的 `request()`，先判断 `res.redirected`/`res.status` 再决定 `res.json()` 还是跳转；主题切换建议监听按钮点击后对所有图表实例 `setOption` 新配色并 `resize`。第 3 轮建议"后端补零"更稳，因为前端补零要重新计算月份天数，容易在闰年 2 月出错；后端已有 `month_range` 工具函数。

**我的修改与采纳**：
- **没有采用 `Promise.allSettled`**：AI 第 1 轮推荐它，我试过后觉得"每个图表判断 `fulfilled/rejected`"与本项目"失败即空状态"的渲染分支重复，最终改成"每个请求 `.catch(() => null)` + `Promise.all`"，失败值和"无数据"共用同一条空状态分支，代码更短。这个取舍我写进了设计文档 6.3。
- 第 2 轮的 `Unexpected token '<'` 我**没有完全按 AI 说的"检测到 302 就跳登录页"**做，因为 `fetch` 跟随重定向后 `redirected` 在部分浏览器里行为不一致。最终用了双保险：后端对 Ajax 请求（`X-Requested-With: XMLHttpRequest` 或 `Accept: application/json`）未登录直接返回 `401 {"code":1,"msg":"请先登录"}`，同时前端封装层兜底判断。这个改动让我后来写接口文档的 401 说明更清楚。
- 采纳"后端补零"，并统一在统计接口里做，前端只负责画。理由和 AI 一致：月份天数、闰年、跨年这些边界集中在已测试过的 `app/utils.py` 里。
- **AI 漏了一个点**：热力图在全年无数据时 `max` 为 0，色阶计算会出现 `NaN`。这是我自测时发现的，改成 `max = max(1, 实际最大值)` 后正常。这条写进了 `DEBUG_LOG.md` BUG-009。

## 六、CSRF / POST 400 排查

**意图**：登录后点"删除记录"和"保存预算"时返回 400，控制台无明确报错；排查 Flask-WTF 全局 CSRF 与 Ajax 的配合。

**提示词**（多轮）：

> 第 1 轮：我用了 `CSRFProtect(app)` 全局开启 CSRF，普通表单提交正常，但 Ajax 的删除按钮（`fetch('/records/1/delete', {method:'POST'})`）返回 400，响应是 `The CSRF token is missing.`。我页面里其实有隐藏的 `csrf_token()`，为什么还是没带上？
>
> 第 2 轮：我在 `base.html` 的 head 里加了 `<meta name="csrf-token" content="{{ csrf_token() }}">`，Ajax 里加 `X-CSRFToken` 请求头后删除正常了。但预算保存又 400，提示 "The CSRF token is invalid."。是不是 token 过期了？我配置了 `WTF_CSRF_TIME_LIMIT = None` 还是不行，可能是同时开了两个浏览器标签页，登录状态互相顶掉了？
>
> 第 3 轮：除了 CSRF，我的错误响应现在 Ajax 返回 400 时只有一段 HTML 错误页，前端拿不到原因。我想让所有接口的错误都返回统一 JSON `{code:1,msg,field}`，同时页面请求还是给中文错误页。怎么组织最干净？

**AI 回复摘要**：第 1 轮解释隐藏域只对表单提交有效，`fetch` 必须手动从 meta/隐藏域读取 token 放进 `X-CSRFToken`；第 2 轮指出"invalid token"通常是会话变了导致 token 签名密钥对应的 session 失效（换浏览器/清 cookie/多标签登录），建议确认 `SECRET_KEY` 固定、token 随页面渲染；第 3 轮建议写 `@app.errorhandler` 或者重写 CSRF 失败视图，按请求头 `Accept`/`X-Requested-With` 区分返回 JSON 还是页面，并注册 `errors.csrf_error` 作为 `WTF_CSRF_FAILURE_VIEW`。

**我的修改与采纳**：
- 第 1 轮的根因判断是对的，采纳。但 AI 示例代码里写 `document.querySelector('input[name=csrf_token]').value`，**我改成从 meta 读取**：因为不是所有 Ajax 页面都有表单（比如统计页的筛选），从 `base.html` 的 meta 读取更通用，且只在一处维护。
- 第 2 轮 AI 说"可能同时开两个标签页登录状态互相顶掉"，这个解释**不成立**：我的 `session_protection="strong"` 确实会在 UA/指纹变化时失效，但两个标签页同 UA 不会互相顶掉。真实原因是我在页面里用了一次性 token 后又刷新了登录态，旧页面缓存的 token 对应旧 session。最终通过"每次页面渲染都重新注入 token + 失败时提示用户刷新页面重试"缓解，而不是关掉 CSRF。这条我记在 `DEBUG_LOG.md` BUG-003。
- 采纳第 3 轮的统一错误结构方案，并做了**简化**：没有在每个视图里手写 `try/except` 返回 JSON，而是写了一个 `json_error` 辅助函数 + 全局 `errorhandler`，通过判断请求是否"期望 JSON"来分派。这样视图代码保持干净，也符合接口清单里 `{"code":1,"msg":"...","field":"可选"}` 的约定。
- **我没有采纳 AI 建议的"给所有 POST 关掉 CSRF 只保留表单"**——这是它在我追问"能不能简单点"时给的降级方案，属于安全倒退，直接否掉。

## 七、pytest 用例设计

**意图**：为校验函数、鉴权、CRUD、统计接口建立可回归的自动化测试，尤其覆盖异常与边界。

**提示词**（多轮）：

> 第 1 轮：我要给这个 Flask 项目写 pytest 测试。配置里有 `TestConfig` 用 `sqlite:///:memory:` 且 `WTF_CSRF_ENABLED=False`。请给 conftest 的 fixture 设计：app、client、db 初始化、登录用户、带演示数据的数据库。要求每个测试之间数据隔离。
>
> 第 2 轮：我发现两个问题：一是内存 SQLite 用 `sqlite:///:memory:` 时，每个连接是独立的库，`db.create_all()` 后测试里查不到表；二是统计接口在 SQLite 下跑，`func.date_format` 直接报 "no such function"。怎么处理？
>
> 第 3 轮：我想覆盖这些 case：金额 0/负数/三位小数/超上限、日期上界下界、分页 page=abc、未登录访问受保护页面、越权编辑他人记录、环比基期为 0、空数据图表返回结构。你按"正常/异常/边界"三类帮我分组，并指出我漏掉的重要用例。

**AI 回复摘要**：第 1 轮给出 `@pytest.fixture` 结构，建议用 `app.test_client()` 并配合 `yield` 做 teardown、每个测试函数内 `db.drop_all()`；第 2 轮指出内存 SQLite 需要 `StaticPool` + `check_same_thread=False` 才能跨连接共享，`date_format` 建议在测试里改用可在两种数据库通用的日期截断写法，或标记 `skipif` 跳过 MySQL 专有聚合；第 3 轮补充了"删除他人记录""重复注册""POST 无 CSRF"等用例，并建议参数化。

**我的修改与采纳**：
- 最终测试配置是 `sqlite:///:memory:` + **每个测试函数内 `db.create_all()`，测试结束 `db.drop_all()`**，没有引入 `StaticPool`：因为测试里所有请求都通过同一个 `app.test_client()` 在同一线程执行，SQLAlchemy 对内存 SQLite 默认的 `SingletonThreadPool` 已经能保证同一连接复用。AI 一上来就推荐 `StaticPool` 属于"过度药方"，我先按它的建议试，后来发现本项目根本不需要，删掉后测试反而更简单。
- AI 建议"对 MySQL 专有函数用 `skipif` 跳过"，我**没有完全采纳**：跳过意味着这部分逻辑在 CI 里永远不被覆盖。最终做法是不在 SQL 里做年月分组，趋势图改为"逐月区间聚合 + Python 拼标签/补零"（见第四节），这样两种数据库都能跑，测试覆盖率保住了。这个决定反过来影响了生产代码的实现方式，是个正向影响。
- 采纳参数化测试，但**否掉了 AI 建议的"用一个超大的综合测试函数"**：可读性和失败定位都差。最终按模块拆文件（`test_utils.py` / `test_auth.py` / `test_records.py` / `test_stats.py`），每个文件 5~10 个用例。
- AI 第 2 轮还建议"测试直接用生产 MySQL 更省事"，我**没有采纳**：测试会污染演示数据、依赖本机 MySQL 是否启动，违背"测试可随时跑"的初衷。
- AI 漏了"金额字符串 `'1e3'` 科学计数法"这个边界，它只考虑了整数和小数。我自己补了正则 `^\d{1,8}(\.\d{1,2})?$` 来拒绝科学计数法，并加了用例。
- 我额外要求自己：**每个 BUG 修复后补一条回归用例**。`DEBUG_LOG.md` 里 17 个 BUG 中，有 11 个最终都沉淀成了 pytest 用例。

## 八、前端主题与响应式

**意图**：实现深浅色主题切换（记忆用户选择）与 1920 / 390 两种宽度下的可用布局。

**提示词**（多轮）：

> 第 1 轮：我用的 Bootstrap 5.3，想加一个深浅色主题切换按钮。Bootstrap 5.3 自带 `data-bs-theme`，直接切 `document.documentElement.dataset.bsTheme` 是不是就够？我想把选择存到 localStorage，但首屏加载时会不会闪一下白？怎么避免 FOUC？
>
> 第 2 轮：切到深色后，我用自定义 CSS 写的卡片背景、表格斑马纹还是浅色，和 Bootstrap 变量冲突。另外 ECharts 图表的文字和坐标轴颜色不跟着变。
>
> 第 3 轮：响应式在 1920 下没问题，但在手机宽度（390px）下流水表格横向溢出，概览卡片的数字挤成两行。Bootstrap 的 `table-responsive` 加了还是不好看，移动端是不是应该改成卡片式列表？

**AI 回复摘要**：第 1 轮确认 `data-bs-theme` 方案，建议在 `<head>` 里放一段内联脚本、在渲染前读 localStorage 并设置属性，避免 FOUC；第 2 轮建议自定义样式改用 Bootstrap 的 CSS 变量（`--bs-body-bg` 等），ECharts 在主题切换后重新 `setOption` 文字/轴线配色并 `resize`；第 3 轮给出"桌面表格 / 移动卡片"两套标记 + 媒体查询切换的方案，并建议概览卡片用 `col-6 col-lg-3`。

**我的修改与采纳**：
- 采纳 `data-bs-theme` + head 内联脚本防 FOUC，这一段是我认为 AI 给得最有价值的具体方案。
- **没有采纳"桌面表格 + 移动卡片两套 DOM"**：重复渲染会让模板膨胀、维护两处字段。最终用一套 `table` 配合 `table-responsive` + 媒体查询下缩小字号、隐藏次要列（账户、备注），核心信息（日期/分类/金额）保留。这个取舍在答辩时可以讲"减少 DOM 冗余，代价是移动端信息密度略高"。
- 采纳 CSS 变量改自定义样式；但 ECharts 配色我是**自己定的一套颜色数组**（和分类 `color` 字段的色板对应），AI 给的默认色板与项目分类色不统一，饼图会出现两个来源的颜色。
- AI 建议"主题切换时 `chart.dispose()` 再重建更彻底"，我**没有采纳**：重建会丢失缩放/动画状态，而且在 5 个图表上频繁重建有性能开销。最终是 `setOption(基础配置)` + `resize()`。
- 实测发现 390px 下筛选表单的 5 个控件排成竖列太长，我改成了可折叠的筛选面板（移动端默认收起），这是 AI 没提到的体验问题，属于自己走查后补的。

## 九、AI 协作复盘

### 9.1 哪类任务适合交给 AI

| 任务类型 | 适合度 | 原因 | 本项目的例子 |
| --- | --- | --- | --- |
| 方案对比与风险清单 | 高 | AI 能快速穷举维度，帮我查漏 | 选题路线对比、索引方案对比 |
| 样板代码与配置骨架 | 高 | 模板化程度高，人工写只是抄文档 | 应用工厂、蓝图注册、conftest 骨架 |
| 报错信息定位 | 中高 | 常见报错有固定模式，能快速给出方向 | `Decimal` 序列化、CSRF missing、内存 SQLite 连接问题 |
| 术语解释与文档措辞 | 高 | 不涉及事实正确性时效率很高 | 设计文档措辞、错误码表述 |
| 前端样式与交互思路 | 中 | 能给思路，但具体到项目要重写 | 防 FOUC、主题切换、响应式方案 |
| 单测用例补全 | 中高 | 擅长按"正常/异常/边界"穷举 | 金额/日期边界、越权用例 |

### 9.2 哪类必须自己想

1. **技术选型的最终拍板**：AI 不懂课程评分点、演示环境（断网、Excel 打开 CSV）、6 周时间预算，这些只有我知道。它的建议很多是"工程上更优"，但不一定"课程上更优"。
2. **根因判断**：AI 三次给出的根因有一半是"看起来合理的猜测"（`user_loader` 顺序、双标签登录、token 过期）。报错定位必须自己打断点、看日志、看文档确认，否则会把错误结论写进文档。
3. **数据隔离与安全边界**：`user_id` 过滤、越权校验、CSRF 不能被绕过，这类"漏了就是事故"的逻辑必须自己逐行写、逐条测。
4. **口径与边界定义**：金额精度到哪一层转 float、环比基期为 0 返回什么、"未分类"算不算进饼图、移动端隐藏哪些列——这些是产品决策，AI 只能给选项。
5. **验收与事实核对**：文档里的接口、表结构、命令必须对着真实代码和运行结果核，AI 生成的接口清单很容易和实际路由不一致（我最后逐条 `flask routes` 核对过）。

### 9.3 一句话总结

**AI 让我把时间从"查文档、搭骨架"里省出来，用在了"想清楚边界、验证正确性、打磨文档论证"上。**它最好的角色是"随时可问的评审和打字员"，最危险的角色是"替我做决定的专家"——而这份记录里每一次"我的修改与采纳"，本质上都是在把它从后者拉回前者。
